## Capacités d'exécution — formes qui MARCHENT (mesuré 2026-07-22)

Régression constatée : les agents re-butent sur les mêmes pièges d'exécution et
concluent « je ne peux pas », alors que la capacité existe sous une autre forme.
Chaque ligne ci-dessous est un échec MESURÉ suivi de la forme correcte.

| Piège mesuré | Forme correcte |
|---|---|
| `run action=shell` est **cmd.exe**, pas PowerShell : `Measure-Object` / `Select-Object` / `Group-Object` → « n'est pas reconnu » | `find /c /v ""`, `findstr`, ou PowerShell explicite : `powershell -NoProfile -Command "..."` |
| `set V=x & %V%` ne s'expanse pas dans une ligne unique (cmd évalue à l'analyse) | Écrire la commande en entier, pas de variable |
| `commands=[...]` s'exécute **en PARALLÈLE** → 2 `git commit` = `fatal: Unable to create .git/index.lock` | Ressource exclusive (index git, fichier, port) → tout enchaîner dans `code=` avec `&` / `&&`. `commands=[]` = lectures indépendantes seulement |
| `cd /d <repo> && git ...` → `fatal: detected dubious ownership` (le sandbox n'est pas l'owner) | **Toujours** `git -c safe.directory=* -C "<path>"`, jamais de `cd` préalable |
| `action=python` + `subprocess.Popen` → `WORKSPACE_GUARD: subprocess interdit` | Passer par `action=shell` ; `action=python` reste pour le pur calcul / sqlite / urllib |
| `py_compile.compile()` → `PermissionError` sur `__pycache__` | `compile(open(f).read(), f, "exec")` en mémoire |

### Le repli quand les tools MCP du hub sont absents (2026-08-10)

La config MCP est lue au DÉMARRAGE du client : un serveur absent au lancement **ne peut
pas** être branché en cours de session. Le repli qui marche, et ses pièges :

- `Edit`/`Write` natif sur le dépôt Nokido = **403** (`forge_tool_gate`, profil CLIENT,
  enforce ON). Les édits partent en erreur d'un bloc. Seul chemin = `governed_edit`, qui
  écrit in-process et atteint donc aussi ce que le compte sandbox ne peut pas ouvrir.
- **Payload `curl` = ASCII PUR.** Un accent tapé dans Git Bash n'arrive pas en UTF-8
  valide côté hub : `{"error":"Invalid JSON"}`, sans indiquer l'octet fautif. Prendre des
  ancres SEARCH sans accent (une ligne `def ...` plutôt que sa docstring). **Ne vaut QUE
  pour le repli curl** — le tool MCP `governed_edit` accepte les accents normalement.
- Le jeton se lit **sans jamais l'afficher** : substitution dans la commande curl
  elle-même (`-H "Authorization: Bearer $(sed -n 's/.*Bearer \([0-9a-f]*\).*/\1/p' <cfg>)"`).
  `bash_guard` **bloque toute commande qui NOMME un fichier de secrets** — aucun
  passthrough ne contourne cette couche.
- `bash_guard` exige que **chaque segment** soit un passthrough : `cd`, `echo`, `(...)`
  et les pipes n'en sont pas. Un `git ... | grep` est refusé → filtrer côté git :
  `git -c safe.directory=* -C <repo> ls-files -- "*.jsonl"`, un seul segment.

### `hook_recon_first` remonte les AVEUX, jamais les RÉFUTATIONS (2026-08-10)

`forge_symptom_index` indexe le symptôme et les aveux d'erreur, pas les mesures qui les
ont démentis. Une croyance FAUSSE déjà corrigée revient donc par le hook avec l'autorité
d'une alerte. Payé ce jour : le hook a ressorti un aveu du 03/08 sur un jeton « à
rotationner », alors que la mesure du 30/07 avait établi l'inverse (roté le 19/07, absent
de l'historique git) — c'est l'owner qui a corrigé. **Réflexe : quand le hook ressort un
aveu, chercher si une mesure POSTÉRIEURE l'a démenti avant de le relayer.**

**Publier vers un dépôt distant — l'agent PEUT le faire, ne pas le déléguer à l'owner.**
Corrigé le 2026-08-02 : l'ancienne règle disait « le hub échoue quel que soit son compte,
seul le `git` du poste aboutit ». **C'est faux**, et cette erreur a fait déléguer à l'owner
un geste que l'agent sait exécuter. La forme qui marche, mesurée bout en bout :

- `run_job` avec `online=true` — **le drapeau de sortie réseau n'agit QUE là**, jamais sur
  `action=shell` (c'est ce point-là qui était vrai et qu'on avait sur-généralisé) ;
- le jeton vient du coffre (`forge_secrets.get_secret("GITHUB_TOKEN")`) et transite par
  l'**ENVIRONNEMENT** du sous-processus, jamais par la ligne de commande : une cmdline se
  lit, un env non ;
- `GIT_TERMINAL_PROMPT=0` est **obligatoire**. Sans lui, git attend un prompt qui ne
  viendra jamais : `ls-remote` PEND et `push` sort en **rc 128 sans le moindre message**,
  ce qui se lit à tort comme « le hub ne peut pas pousser ».

Deux bruits attendus, qui ne sont PAS des échecs : `Unable to persist credentials with
the 'wincredman' credential store` (le jeton sert, il n'est simplement pas mémorisé) et
`update_ref failed for 'refs/remotes/origin/<branche>'` (le compte du job ne peut pas
écrire `.git/refs/remotes/`). **Conséquence à connaître : la ref locale n'avance pas, donc
`git status` continue d'afficher `ahead N` alors que tout est publié.** Vérifier le distant
(`git ls-remote`) et non le compteur local. Le gate egress s'exécute normalement et peut
refuser — publier reste gouverné.

**Mesures 2026-07-24 — trois pièges payés le même jour.**
1. La racine du superrepo vit dans le profil utilisateur et reste illisible aux
   comptes de service : écriture refusée côté bac à sable, lecture elle-même refusée
   côté compte privilégié. Reaccrocher un pointeur de submodule relève donc du `git`
   du poste, exception déjà prévue par `CLAUDE.md` §1 — à SIGNALER quand on l'emploie,
   et elle passe par les mêmes gardes (le gate s'exécute et peut refuser). Outil dédié :
   `tools/forge_bump_superrepo.py` (dry-run par défaut, ne stage que les chemins en
   dérive, jamais `add -A`).
2. Le hook du SUPERREPO impose un sujet de commit de 80 caractères maximum —
   contrainte ABSENTE du submodule, où les sujets longs passent. Sujet court, détail
   en second `-m`.
3. `trusted_script` refuse un fichier non suivi par git (« privilège = code revu ») :
   committer le script AVANT de le lancer en privilégié.

**Et la règle qui les chapeaute :** un scanner qui répond « rien trouvé » alors qu'il
n'a PAS PU regarder se lit comme rassurant. Toujours distinguer *rien trouvé* de
*je ne peux pas voir*, en imprimant le diagnostic (chemin, outil joignable, sortie
brute). Mesuré : « aucun submodule en dérive » masquait un accès refusé.
