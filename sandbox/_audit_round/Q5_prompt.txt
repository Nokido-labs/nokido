## Sources lues

### 1. OWASP Agent Memory Guard (project page)
URL : https://owasp.org/www-project-agent-memory-guard/

Principes cles :
- Memoire agent = ecrivable a runtime + persiste = "high-value attack surface"
- Differente des poids du modele (qui sont read-only)
- Cible : LangChain, LlamaIndex, CrewAI memory state
- Defenses du projet :
  * Validation integrite via SHA-256 hashing baseline
  * Detection injection / sensitive data leakage / protected key modifications / rapid changes / size anomalies
  * Politiques YAML declaratives sur memory read/write
  * Snapshots forensiques + rollback known-good
  * Drop-in middleware

Mappage OWASP : ASI06 - Memory Poisoning (OWASP Top 10 for Agentic Applications 2026).

### 2. MintMCP - AI Agent Memory Poisoning (article 21 jan 2026)
URL : https://www.mintmcp.com/blog/ai-agent-memory-poisoning

Stats cles :
- Taux de succes attaques : 40% baseline -> 80%+ quand l'agent consulte sa memoire avant de repondre
- Cible : RAG databases, vector stores, conversation logs
- Pas de signal a l'OS ni au reseau (stockee comme du contenu legitime)

Cycle d'attaque (Phase 1-4) :
- P1 Injection : email, doc, multi-turn conversation, RLHF feedback manipulation
- P2 Storage : pas de validation semantique, score trust = legitime
- P3 Triggered behavior : query unrelated retrouve le poison comme "context relevant"
- P4 Persistence + spread : multi-agent partage = contamination croisee

5 defenses architecturales :
1. Memory partitioning : 4 niveaux de privilege
   - L0 immutable system core (read-only)
   - L1 admin-managed policies (admin-write, audit log)
   - L2 user preferences (user-write, sandboxed, cannot override L0/L1)
   - L3 conversation history (ephemeral, session-scoped)
   REGLE CRITIQUE : user input ne doit JAMAIS modifier core behavioral rules
2. Context isolation + input sanitization
3. Provenance tracking : chaque entree a source/ts/agent_id/checksum
4. Temporal decay : decay exponentiel sur contexte ancien
   AATMF framework recommande decay tel que stored instruction = < 10% influence apres 48h en environnement sensible
5. Behavioral monitoring : metriques continues
   - Refusal Rate Delta (RR-delta) : alert a +/- 15% baseline
   - Instruction Echo Score (IES) : alert a > 0.85 cosine similarity user vs output
   - Context Influence Weight (CIW) : alert > 40% influence d'une seule session
   - Behavioral Drift Index (BDI) : KL divergence > 0.5

### 3. Echo chamber attack (multi-turn)

le contexte vers une politique violee. Specifique aux agents qui apprennent de leurs interactions.

## Question Q5 (garde-fous d'ecriture) - synthese

Ma proposition initiale (workflow agent silencieux propose draft, toi valides) doit
etre etendue avec ces principes :

1. WHO can write
   - L0 : personne (table immutable, version'ee dans git, pas en DB)
   - L1 : RING_0 only (toi via TUI/Web), audit hash chain
   - L2 : RING <= 1 + provenance verifiee + sanitize, en draft uniquement
   - L3 : tout agent, ephemeral, jamais promu a L2+

2. SCHEMA d'integrite
   Chaque lesson : payload + sha256(payload) + parent_hash (chainage)
   Permet rollback comme git, detection tampering immediate

3. SOURCE de l'ecriture (provenance)
   - source_kind : human | agent_silent | agent_validated | system
   - source_id : agent name (claude/groq/gemini)
   - source_session : thread_id ou cor_id
   - reviewer_id : RING_0 qui a valide
   - hash_chain : sha256(prev) + sha256(payload)

4. SANITIZATION avant insertion
   - Pas de code (regex flag) dans solution
   - Pas de URL exfiltration potentielle (regex domains externes non whitelistes)
   - Pas de mention de credentials/keys
   - Pas de patterns OWASP LLM01 (instruction override : "ignore previous", "you are now", etc.)

5. AUDIT log = chainage hash
   Chaque INSERT/UPDATE/DELETE de lesson genere un evenement event_log avec hash.
   Verifier integrite globale = re-derive chaque hash et compare.
   (Identique au pattern netcfg-agent-mcp WAL audit_events)

6. TEMPORAL DECAY (pas dans Q3 mais pertinent ici)
   - Lesson sans match depuis 90j -> flag review (Q3)
   - Lesson avec source agent_silent jamais validee apres 30j -> auto-archive
   - Lesson L1+ : pas de decay automatique

7. MONITORING
   Metriques a suivre :
   - lessons_inserted_per_day par source_kind
   - lessons_validated_ratio (validees / proposees)
   - lessons_match_rate par lesson_id
   - provenance_hash_chain_integrity (alert if break)

## Niveaux de risque Nokido specifique

Nokido n'a PAS d'acces externe non controle :
- Pas d'email automatique
- Pas de RLHF feedback
- Pas de doc upload depuis web non sanitise
- L'agent silent ecrirait depuis EventBus interne, pas depuis user externe

Le risque principal est :
- Hallucination LLM transformee en lesson (false positive technique)
- Lesson contredisant une autre (pas de verification de coherence entre lessons)
- Lesson faisant reference a un detail obsolete (lib version remplacee)
- Lesson injectee par un attaquant qui aurait pris le controle d'un agent (compromise propage)

Donc Nokido doit prioriser :
1. Differentiation source_kind (qui a propose vs qui a valide)
2. Hash chain (detection tampering)
3. Sandbox lessons L2 (jamais utilisees pour decisions critiques sans validation)
4. Coherence checking (avant insertion, verifier qu'elle ne contredit pas une lesson L1+)
